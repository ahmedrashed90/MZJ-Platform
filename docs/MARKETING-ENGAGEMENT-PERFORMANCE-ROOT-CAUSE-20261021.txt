MZJ PLATFORM - MARKETING ENGAGEMENT PERFORMANCE ROOT-CAUSE REVIEW
2026-10-21 | Complete clean source release (not a patch)

SYMPTOMS OBSERVED IN PRODUCTION SCREENSHOTS
- Platform connection cards stayed at loading status.
- Organic engagement, followers, and campaign-results tabs stayed loading.
- Previously, new Google Ads reports increased API and DB load.

CODE FINDINGS AND IMPLEMENTED CHANGES
1) Site-wide authentication overhead: server/_auth.ts verifies attendance on each session.
   The previous server/_attendance-schema.ts ensureAttendanceSchema ran the entire
   attendance ALTER TABLE / CREATE INDEX migration and legacy-record import on
   every serverless cold start, even when the schema was current. This is a
   concrete risk of PostgreSQL DDL locks blocking read requests. The schema
   migration now runs ONLY when a comprehensive schema readiness check fails,
   under the existing advisory lock. Attendance business rules and SQL migration
   definitions were NOT changed.
2) Read-only marketing and OAuth connections status requests no longer run
   marketing schema DDL. OAuth callbacks and write requests keep their existing
   migration safety checks.
3) Engagement tabs query only their needed data: organic posts/engagements,
   Meta account follower snapshots, or campaign/agenda result aggregates.
   Previously every tab loaded all of them, including unnecessary CRM joins.
4) Meta follower accounts load independent aggregate queries concurrently;
   if there are no accounts, no unnecessary aggregate queries are executed.
5) Engagement UI cancels obsolete tab requests and polls only when visible,
   with a bounded 20-second error state and explicit retry. It defers automatic
   visible Meta refresh and avoids displaying misleading zeros during loading.
6) Meta and Google paid panels have request timeouts; all-providers view
   staggers Google by two seconds to reduce concurrent cold-start requests.
7) Platform connection cards remain visible during transient status failures.
8) Slow endpoints emit timing warnings in Vercel logs (no account tokens logged).

- 102/102 Marketing workflow checks.
- 25/25 Platform integration tests.
- Other scoped attendance, engagement, comments, publishing tests pass.
- One older Meta fresh-metrics script currently fails on BOTH the original

  This is not represented as passed and is outside the altered paths.

LIMITATIONS
- The live Vercel production runtime logs were inaccessible (403 forbidden).
- No production DB, real OAuth provider calls, or real end-user timing test
  was possible in this environment. A measured latency improvement is not
  claimed without a live, authorized measurement.
- Full production build could not be run here, because the package registry
  was inaccessible and a complete node_modules install was unavailable.
- No live production deployment was performed by this release.

AFTER DEPLOYMENT
- Deploy the entire ZIP as source (not selected files or a separate patch).
- Preserve all existing Vercel environment variables and PostgreSQL contents.
- Verify build is READY, then first open Marketing > Connections, Followers,
  Organic Engagement, Campaign Results, and Meta/Google Paid Reports.
- Check Chrome DevTools Network for API response times and errors; if a specific
  path remains slow, send its status/duration plus Vercel Function runtime
  log from the same request. Slow GETs >=2.5s are logged with their category.
- If business-critical pages are unusable, Vercel can roll back to the last
  deployment known to be healthy while reviewing this version.

NO CHANGES TO
- YouTube credentials, OAuth scopes or publishing behavior.
- Google Ads or Meta token values, campaigns or campaign amounts.
- Attendance policy calculations, CRM business logic, branch/sales permissions.

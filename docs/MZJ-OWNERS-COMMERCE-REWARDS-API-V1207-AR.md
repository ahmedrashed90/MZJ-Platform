# MZJ Owners Community — Referral Rewards Commerce API v1207

## النطاق

هذا التعديل محصور داخل MZJ Owners Community والمكافآت وواجهة الربط مع موقع شراء السيارات. لا يغيّر نظام CRM أو Tracking أو Operations أو Marketing أو تكاملات Next ERP القائمة.

## الفكرة

- كود الشراء هو نفس `referral_code` الحالي للعضو؛ لا يوجد نظام كوبونات منفصل.
- صاحب العضوية يستطيع مشاركة نفس الكود مع أكثر من عميل جديد.
- العميل الجديد يرى مكافآت العميل الجديد ومكافآت العميل القديم حسب إعداد الكتالوج. بعد تسجيل أول استفادة مؤكدة يصبح استخدامه التالي ضمن فئة العميل القديم، ويمكنه الاستفادة من مكافآت العميل القديم في طلبات شراء لاحقة. يمنع التكرار لنفس رقم طلب الموقع فقط.
- فلو الإحالة الحالي يبقى كما هو: `registered -> qualified -> sold`.
- نقاط صاحب الدعوة تستمر من نفس النظام الحالي ولا تعتمد على مجرد اختيار المكافأة.
- الإدارة تحدد من كتالوج المكافآت أي مكافآت متاحة لعميل الموقع عند استخدام كود الدعوة.

## إعداد المكافأة من المنصة

تمت إضافة إعدادين للمكافأة:

1. `متاحة للعميل الجديد عند استخدام كود الدعوة في طلب الشراء`
2. عند نوع `خصم`: `قيمة الخصم في طلب الموقع (ريال)` وهي قيمة رقمية مستقلة عن النص المعروض في `reward_value`.

الهدية أو الخدمة أو القسيمة ترجع للموقع بقيمة خصم مالية `0`، بينما مكافأة الخصم ترجع بالقيمة المحددة بالريال.

## الأمان

أضف متغير بيئة في مشروع المنصة:

`OWNERS_COMMERCE_API_KEY`

البلجن يرسل نفس القيمة في الهيدر:

`x-mzj-owners-api-key: <secret>`

يجب أن تتم استدعاءات Commerce API من Backend البلجن فقط، وليس من JavaScript في المتصفح.

## Endpoint

المسار الحالي نفسه:

`POST /api/owners/public`

### 1. التحقق من كود الدعوة وجلب المكافآت

Body:

```json
{
  "action": "commerce_rewards",
  "code": "ABC123XYZ",
  "phone": "9665XXXXXXXX"
}
```

Response ناجح:

```json
{
  "ok": true,
  "eligible": true,
  "referralCode": "ABC123XYZ",
  "referrerName": "اسم صاحب العضوية",
  "rewards": [
    {
      "id": "uuid",
      "name": "خصم 1000 ريال",
      "description": "...",
      "type": "discount",
      "value": "1000 ريال",
      "discountAmount": 1000,
      "startsAt": null,
      "endsAt": null
    }
  ]
}
```

التحقق يرفض الحالات التالية من نفس قواعد Owners Community الحالية:

- الكود غير صالح أو العضو غير نشط.
- استخدام صاحب العضوية لكوده لنفسه.
- العميل عضو حالي أو سبق له الشراء.
- العميل مرتبط بكود دعوة مختلف.
- العميل سبق أن استفاد من مكافأة كود دعوة في طلب شراء.

### 2. تأكيد المكافأة وربطها بطلب الموقع

يُستدعى بعد تحديد المكافأة ومع وجود رقم طلب موقع فريد. يعيد التحقق من الكود والمكافأة ولا يعتمد على بيانات الواجهة.

Body:

```json
{
  "action": "commerce_confirm",
  "code": "ABC123XYZ",
  "phone": "9665XXXXXXXX",
  "name": "اسم العميل الجديد",
  "rewardId": "reward-uuid",
  "websiteOrderId": "12345",
  "nextErpSalesOrder": "SAL-ORD-2026-00001"
}
```

`nextErpSalesOrder` اختياري. ويمكن استدعاء `commerce_confirm` مرة أخرى بنفس `websiteOrderId` بعد إنشاء طلب البيع في Next ERP لتحديث رقم طلب البيع؛ العملية Idempotent ولا تُحسب المكافأة مرتين.

Response:

```json
{
  "ok": true,
  "referralId": "uuid",
  "benefitId": "uuid",
  "referralCode": "ABC123XYZ",
  "reward": {
    "id": "uuid",
    "name": "خصم 1000 ريال",
    "type": "discount",
    "value": "1000 ريال",
    "discountAmount": 1000
  }
}
```

## الحفاظ على فلو العملاء

`commerce_confirm` يستخدم نفس منطق تسجيل الإحالة الحالي بدل إنشاء مسار عملاء جديد:

- إنشاء/ربط CRM Lead بنفس مصدر `owners_referral`.
- نفس Assignment الحالي.
- نفس سجل `owners.referrals`.
- نفس نقاط التسجيل الحالية.
- نفس مزامنة `qualified` و`sold` من CRM والمبيعات الفعلية.
- نفس إنشاء عضوية جديدة للمشتري بعد البيع.

## المخزون

`stock_quantity` أصبح يحسب الاستهلاك من المصدرين معًا:

- استبدال الأعضاء بالنقاط (`redeemed_quantity`).
- مكافآت الشراء بكود الدعوة (`referral_purchase_redeemed_quantity`).

وبالتالي الهدية محدودة الكمية لا تتجاوز الكمية المحددة حتى لو استُخدمت من القناتين.


## تكرار مكافآت العميل القديم

يمكن للعميل القديم استخدام مكافآت العميل القديم في أكثر من طلب شراء مختلف. يحتفظ النظام بسجل مستقل لكل طلب موقع، ويمنع فقط تكرار نفس `websiteOrderId`. وجود استفادة سابقة لا يمنع التحقق من كود الدعوة في طلب جديد، بل يجعل العميل ضمن فئة `existing`.

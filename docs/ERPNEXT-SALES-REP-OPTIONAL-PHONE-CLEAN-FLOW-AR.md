# تكامل NEXT ERP — فصل مندوب البيع عن إداري العمليات ودعم العميل بدون جوال

## المصدر

تم التنفيذ مباشرة على النسخة المرفوعة:

`MZJ-Platform-main (12).zip`

لم يتم نقل كود من نسخة قديمة، ولم تتم إضافة Endpoint بديل أو Patch جانبي أو Migration تعويضية.

## 1. هوية مندوب البيع

مندوب البيع لا يُستنتج من الشخص الذي نفّذ `Submit`.

Webhook يقرأ مندوب البيع من أول صف في `Sales Team`:

`Sales Order.sales_team[0].sales_person`

ثم يحل الربط داخل NEXT ERP بهذا التسلسل:

`Sales Person.employee` → `Employee.user_id`

ولو كان `user_id` فارغًا، يستخدم `company_email` ثم `personal_email` كبديل داخل بيانات الموظف نفسه.

الإيميل الناتج يُرسل في:

- `sales_rep_email`
- `erp_user_id`

ويستخدمه Backend في:

- ربط المندوب بمستخدم المنصة.
- تحديد قسم وفرع CRM.
- إسناد العميل للمندوب الصحيح.
- احتساب سيارات طلب البيع في تقارير المندوب وKPI.

لا يستخدم `owner` أو `modified_by` كبديل لمندوب البيع.

## 2. إداري العمليات

المستخدم الذي نفّذ `on_submit` أو `on_cancel` يُرسل منفصلًا من:

- `operations_admin_email = doc.modified_by`
- `operations_admin_name = frappe.get_fullname(doc.modified_by)`

ويظهر داخل سجل حركات العمليات في حقل «إداري العمليات» دون تغيير «منفذ الحركة» الذي يظل مندوب البيع.

## 3. إنشاء عميل CRM بدون رقم جوال

رقم الجوال لم يعد شرطًا لإنشاء عميل CRM من طلب NEXT ERP.

عند وصول طلب بيع لمعرض آخر بدون جوال:

- يتم إنشاء عميل CRM بحالة «تم البيع».
- يظل رقم الجوال فارغًا `NULL`، دون رقم وهمي.
- يتم ربط العميل بمندوب البيع الحقيقي وفرعه وقسمه.
- يتم ربطه برقم طلب البيع ومصدر `NEXT ERP`.
- لا يظهر تحذير يمنع CRM بسبب غياب الجوال.

## 4. منع التكرار بدون الجوال

يتم التعرف على العميل بواسطة هوية العميل الثابتة في NEXT ERP:

`Sales Order.customer`

تُحفظ هذه الهوية في `crm.contact_identities` بقناة `erpnext`.

بذلك:

- طلب جديد لنفس المعرض يحدّث نفس العميل بدل إنشاء عميل آخر.
- لو أضيف رقم جوال لاحقًا، يتم تحديث نفس العميل ونفس جهة الاتصال.
- لو تطابقت هوية ERP مع عميل، والجوال مع عميل مختلف، يتوقف الربط كحالة ملتبسة بدل الدمج العشوائي.

## 5. Webhooks

تم تحديث الملفين الأصليين:

- `integration-assets/MZJ-ERPNext-Sales-Order-Webhook-JSON.txt`
- `integration-assets/MZJ-ERPNext-Sales-Order-Cancel-Webhook-JSON.txt`

الأول لـ `on_submit` ويرسل `sales_order.submitted`.

الثاني لـ `on_cancel` ويرسل `sales_order.cancelled`.

يجب استبدال JSON الحالي داخل Webhookي NEXT ERP بمحتوى الملفين بعد نشر النسخة.

## 6. ما لم يتغير

- مسار التراكينج ومراحله.
- تحويل السيارة إلى «مباع تحت التسليم» عند الطلب المؤهل.
- دورة الموافقات المالية والإدارية.
- التحويل إلى «مباع تم التسليم» والأرشفة عند إكمال التراكينج.
- ملاحظة الأرشيف النظيفة `طلب البيع SAL-ORD-...`.
- احتساب عدد سيارات الطلب في مبيعات المندوب.
- تصميم الصفحات والصلاحيات وباقي الأنظمة.

## 7. قاعدة البيانات

لا يوجد ملف SQL جديد، ولا يلزم تشغيل SQL يدويًا لهذا التعديل.

الجداول الحالية تسمح بأرقام جوال فارغة، وهوية عميل ERP تُحفظ في جدول الهويات الموجود بالفعل.
